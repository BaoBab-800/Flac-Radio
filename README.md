# Flac-Radio
An open source radio application developed as a learning project.  The project is still in development, and constructive feedback is welcome.

# Архитектурный аудит Flac-Radio

Дата: 2026-02-20  
Область: `lib/src/*` + организационные артефакты в репозитории.

## Краткий вывод

Проект находится в переходном состоянии: в `README.md` зафиксирован целевой план `feature-first + clean boundaries`, но текущая реализация всё ещё близка к «service-first» с частично неиспользуемыми компонентами и разорванной интеграцией между сервисами.

---

## 1) Архитектура приложения: ключевые проблемы

### 1.1. Целевая архитектура задокументирована, но не реализована
- В `README.md` подробно описана новая структура (`features/*`, `shared/*`, строгие слои), но фактический код расположен в `app/data/services` и не следует этой матрице размещения.
- Это повышает вероятность архитектурной деградации: команда ориентируется на один стандарт, код живёт по другому.

**Риск:** высокий (рост техдолга и сложность масштабирования).

### 1.2. Composition root неполный
- В `main.dart` приложение стартует через `MultiProvider`, но в `providers.dart` подключены только `ThemeService` и `RadioStationsRepository`.
- Сервисы локализации, плеера, глобальных настроек и lifecycle либо не подключены, либо не участвуют в жизненном цикле приложения.

**Риск:** высокий (часть логики существует, но фактически «мертвая»).

### 1.3. Приложение работает в режиме test/home-заглушки
- В `FlacRadioApp` в качестве `home` используется `_TestHomePage`.
- `AppRoutes.routes` полностью закомментирован (роутинг как механизм не используется).

**Риск:** средний (сложно расширять UI и навигацию без повторной сборки основы).

### 1.4. Локализация реализована частично
- Есть `AppLocalizationConfig` и `LocalizationService`, но `MaterialApp` не получает `localizationsDelegates`, `supportedLocales`, `locale`.
- В результате сервис локализации не интегрирован в UI.

**Риск:** средний (функционал есть, но не работает end-to-end).

## 2) Оценка сервисов: качество и организация

### 2.1. `ThemeService` — рабочий, но с техническими шероховатостями
Плюсы:
- Простая модель состояния и persist в `SharedPreferences`.

Минусы:
- `setThemeMode` и `setThemeColor` не `await`-ят `prefs.setInt(...)`; при ошибке записи не будет сигнализации.
- Сервис одновременно отвечает и за state-management, и за persistence. Для маленького проекта это допустимо, но в целевой архитектуре это должен быть use-case + repository.

**Оценка:** 6/10.

### 2.2. `LocalizationService` — логика ок, интеграция отсутствует
Плюсы:
- Корректная загрузка/сохранение locale, есть notify.

Минусы:
- Не подключен в providers и `MaterialApp`.
- Расширение `byKey` в `context_l10n_extension.dart` использует ручную map по строковым ключам: при росте количества ключей это хрупко и требует двойного сопровождения.

**Оценка:** 5/10.

### 2.3. `PlayerService` — функционально полезен, но есть критические дефекты состояния
Проблемы:
1. Подписка на `_audioPlayer.playerStateStream` не сохраняется и не отменяется в `dispose` (риск утечки/лишних событий).
2. Ошибки `setAudioSource`/`play` не обрабатываются: падение потока не трансформируется в состояние ошибки.
3. Жёстко зашитые HTTP headers в сервисе — инфраструктурная деталь внутри application-логики.

**Оценка:** 4/10.

### 2.4. `AudioPlayerState` — логическая ошибка в модели
Критично:
- Поле `stopOnBackground` присутствует в state, но `copyWith` не принимает `stopOnBackground` параметром и фактически не может его изменить.
- `operator==` и `hashCode` не учитывают `stopOnBackground`.

Это ломает согласованность состояния и мешает корректной реакции UI/сервисов на изменение этого флага.

**Оценка:** 3/10.

### 2.5. `GlobalSettingsService` vs `AudioPlayerState.stopOnBackground` — дублирование источника истины
- Флаг `stopOnBackground` хранится одновременно в `GlobalSettingsService` и в `AudioPlayerState`.
- `AppLifecycleService` читает флаг из `AudioPlayerState`, а не из глобальных настроек.

Результат: потенциальная рассинхронизация поведения (настройка может измениться, а lifecycle продолжит смотреть в «старый» источник).

**Оценка организации:** 3/10.

### 2.6. `AppLifecycleService` — концепт правильный, интеграция не завершена
- Сервис подписывается на lifecycle через `WidgetsBindingObserver`.
- Но его регистрация/инициализация в DI не видна, а значит в runtime он может никогда не активироваться.

**Оценка:** 4/10.

### 2.7. `settings_access.dart` — лишний уровень абстракции
- Файл содержит только thin-wrapper функции над `context.read/watch`.
- Это увеличивает поверхность API без заметной пользы и усложняет навигацию по проекту.

**Оценка:** 4/10.

## 3) Организация кода и репозитория

### 3.1. В репозитории есть `lib/src/services.zip`
- Бинарный архив рядом с исходниками обычно является лишним артефактом и мешает прозрачности ревью/истории.

**Риск:** средний (шум в репозитории и источник путаницы).

### 3.2. Слабая модульность по фичам
- `radio`, `player`, `settings`, `localization`, `theme` рассредоточены по разным top-level папкам, а не по вертикалям фич.
- Связи между ними происходят через «глобальные» сервисы вместо explicit use-cases.

**Риск:** высокий при расширении продукта.

## 4) Приоритетный план исправлений

1. **Собрать корректный composition root**
    - Подключить все необходимые сервисы в providers.
    - Инициализировать lifecycle-сервис в bootstrap.

2. **Починить модель плеера**
    - Исправить `AudioPlayerState.copyWith/==/hashCode` для `stopOnBackground`.
    - Убрать дублирование источника истины: выбрать один owner флага.

3. **Довести локализацию до рабочего контура**
    - Пробросить `locale`, `localizationsDelegates`, `supportedLocales` в `MaterialApp`.

4. **Убрать архитектурный шум**
    - Удалить/пересобрать `settings_access.dart` только при наличии реальной пользы.
    - Удалить `services.zip` из `lib/src`.

5. **Начать реальную миграцию к feature-first**
    - Минимум с вертикали `settings` (как и описано в README), затем `player`, затем `radio`.

- **Качество сервисного слоя:** 4/10.
